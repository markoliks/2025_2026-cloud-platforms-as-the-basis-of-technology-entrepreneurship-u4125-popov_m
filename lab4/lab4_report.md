# Лабораторная работа №4  
# Разработка инфраструктуры MVP AI-приложения

## Цель работы

Разработать инфраструктуру для MVP AI-приложения с базовой функциональностью, описать варианты развития инфраструктуры на разных этапах роста проекта и обосновать выбор облачных ресурсов.

## Описание приложения

В качестве примера было выбрано MVP AI-приложения AI Support Assistant.

AI Support Assistant — это AI-чатбот для автоматической поддержки клиентов интернет-магазина. Пользователь задает вопрос в чате, приложение обрабатывает запрос, обращается к AI-модели, использует базу знаний компании и возвращает ответ. Также приложение может сохранять историю диалогов и передавать сложные запросы оператору.

Основные функции приложения:

- прием вопросов от пользователей;
- генерация ответов с помощью LLM API / Vertex AI;
- использование базы знаний из Cloud Storage;
- хранение истории диалогов в Firestore;
- логирование и мониторинг работы сервиса.

## Состояние 1. MVP

На первом этапе приложение запускается в минимальной конфигурации.

### Используемые ресурсы

- Cloud Run App — основной backend приложения и простой интерфейс чата.
- Cloud Storage — хранение файлов базы знаний.
- Firestore — хранение истории диалогов и пользовательских сессий.
- LLM API / Vertex AI — генерация ответов AI-моделью.
- Cloud Logging — сбор логов приложения.

### Обоснование

Для MVP выбран Cloud Run, так как он позволяет быстро запустить контейнерное приложение без ручного управления серверами. Сервис автоматически масштабируется и при отсутствии запросов может снижать потребление ресурсов.

Cloud Storage используется для хранения документов и файлов базы знаний. Firestore подходит для хранения истории диалогов, так как не требует сложной настройки и хорошо подходит для быстрого прототипирования.

На данном этапе важно минимизировать стоимость и сложность инфраструктуры.

---

## Состояние 2. Тестирование партнерами

На втором этапе приложение используется ограниченным числом партнеров и тестовых пользователей. Нагрузка становится выше, поэтому инфраструктура расширяется.

### Используемые ресурсы

- Cloud Run Frontend — пользовательский интерфейс приложения.
- Cloud Run Backend — API и бизнес-логика.
- Cloud Storage — хранение документов и файлов.
- Firestore — хранение истории диалогов.
- Pub/Sub — обработка фоновых задач.
- Secret Manager — хранение API-ключей и секретов.
- Monitoring + Logging — мониторинг, логи и диагностика.
- LLM API / Vertex AI — AI-обработка запросов.

### Обоснование

На этапе тестирования frontend и backend разделяются, чтобы упростить развитие приложения. Pub/Sub добавляется для фоновых задач, например обработки документов или долгих запросов к AI-модели.

Secret Manager используется для безопасного хранения ключей доступа к AI API и другим внешним сервисам. Monitoring и Logging позволяют отслеживать ошибки, задержки и поведение пользователей.

---

## Состояние 3. Production

На production-этапе приложение рассчитано на реальных пользователей и стабильную эксплуатацию.

### Используемые ресурсы

- Cloud Run Frontend — frontend приложения.
- Cloud Run Backend — основной API.
- Cloud Storage — хранение базы знаний и пользовательских файлов.
- Firestore — база данных для истории диалогов и сессий.
- Pub/Sub — очередь для фоновой обработки.
- Secret Manager — безопасное хранение секретов.
- Monitoring + Logging — мониторинг состояния системы.
- LLM API / Vertex AI — генерация AI-ответов.

### Обоснование
В production используется более надежная архитектура с разделением компонентов. Cloud Run позволяет масштабировать frontend и backend независимо. Pub/Sub помогает обрабатывать задачи асинхронно и снижает нагрузку на основной backend.

Monitoring и Logging необходимы для контроля ошибок, производительности и стабильности. Secret Manager снижает риск утечки ключей и конфигурационных данных.

## Экономическая модель

Примерная экономическая модель рассчитана для трех этапов развития приложения.

| Этап | Описание нагрузки | Основные ресурсы | Примерная стоимость |
|---|---|---|---|
| MVP | 100–300 пользователей, до 5 000 запросов в месяц | Cloud Run, Cloud Storage, Firestore, Logging, LLM API | $5–30 в месяц |
| Partner Testing | 1 000–5 000 пользователей, до 100 000 запросов в месяц | Cloud Run Frontend, Cloud Run Backend, Pub/Sub, Firestore, Storage, Secret Manager, Monitoring, LLM API | $80–300 в месяц |
| Production | 20 000+ пользователей, 1 000 000+ запросов в месяц | Cloud Run, Firestore, Storage, Pub/Sub, Secret Manager, Monitoring, LLM API | $700–3000+ в месяц |

Основная часть расходов будет связана не с Cloud Run или Cloud Storage, а с использованием AI-модели. Стоимость LLM API зависит от количества запросов, размера контекста и объема генерируемых ответов.

На этапе MVP выбран самый дешевый вариант инфраструктуры, так как главная цель — проверить гипотезу и получить первые отзывы. При росте нагрузки инфраструктура постепенно усложняется: добавляются отдельные сервисы, очереди, мониторинг и безопасное хранение секретов.

## Вывод

В ходе лабораторной работы была разработана инфраструктура MVP AI-приложения AI Support Assistant.

Были рассмотрены три состояния приложения: начальный MVP, тестирование партнерами и production-решение. Для каждого состояния были выбраны подходящие облачные сервисы Google Cloud и описано, почему они подходят для данного этапа.

На первом этапе используется минимальная архитектура на базе Cloud Run, Cloud Storage, Firestore и AI API. На этапе тестирования партнерами инфраструктура расширяется за счет разделения frontend/backend, добавления Pub/Sub, Secret Manager и мониторинга. На production-этапе инфраструктура становится более устойчивой и удобной для масштабирования.

Также была составлена примерная экономическая модель. Был сделан вывод, что на раннем этапе самым рациональным является минимальный набор облачных сервисов, а основная стоимость AI-приложения будет зависеть от количества обращений к AI-модели.
